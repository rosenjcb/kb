\section{Experiments}
\label{sec:experiments}

\subsection{Evaluation Targets}

Harvest evaluation uses a fixed portfolio of ten upstream repositories
(Table~\ref{tab:harvest-results}).  Each suite is a version-pinned git snapshot
with a curated question pack scored by the same LLM-as-judge rubric.

\medskip
\noindent\textbf{Raylib (external benchmark).}  The
\href{https://github.com/raysan5/raylib}{raylib C library} is the primary
\emph{external} target: it is not the KB codebase (eliminating evaluator familiarity
bias), has rich cross-module structure that exercises the document$\leftrightarrow$symbol
hop, and ships stable upstream documentation.  $N_{\text{q}} = 11$.

\medskip
\noindent\textbf{KB self-check.}  Suite \texttt{kb} evaluates KB against its
own codebase---twelve architecture, workflow, and adversarial questions (including
fact-curator and out-of-scope probes).  This smoke test stress-tests retrieval
grounding on a repo whose structure the authors know well.

\medskip
\noindent\textbf{Cross-language portfolio.}  Eight additional suites stress parsers,
retrieval, and product/UI inference across languages and architectural styles:
\texttt{fzf} (Rust CLI fuzzy finder),
\texttt{kestra} (Java orchestration with YAML flows and execute console),
\texttt{shellcheck} (Haskell monadic AST linting),
\texttt{lazygit} (Go TUI),
\texttt{datasette} (Python data-explore/publish UI and CLI),
\texttt{mitmproxy} (Python async proxy and TUI),
\texttt{fish-shell} (Rust systems shell), and
\texttt{brew} (Ruby package-manager DSL).
Each uses $N_{\text{q}} = 8$ multi-step questions spanning capabilities,
architecture, installation, conventions, and gotchas.

\subsection{Protocol: paired K vs N evaluation}

Each evaluation executes, in order:
(1)~clone and index the suite repository (\texttt{kb init} on first use, or reuse
the named session and \texttt{kb scan} on subsequent runs; \texttt{--force-init}
deletes the base and re-runs \texttt{kb init} from scratch);
(2)~$N_{\text{q}}$ \texttt{kb query} calls (condition \textbf{K})---one-shot synthesis
over the curator-kept unit pool (\S\ref{subsec:synthesis});
(3)~the same questions handed to a headless coding agent with no KB
(condition \textbf{N});
(4)~LLM scoring ($\times 3$ averaged) on the five quality axes for both sides,
plus measured token and latency totals;
Question counts vary by suite ($N_{\text{q}} = 12$ for \texttt{kb};
$N_{\text{q}} = 11$ for \texttt{raylib}; $N_{\text{q}} = 8$ for the remaining
suites).

Both sides are scored under identical rubric and success-score formulas; the
headline grade is $\Delta S = S_K - S_N$ (Eq.~\ref{eq:delta-s}).

\subsection{Scoring Rubric}

Each suite covers questions spanning capabilities, architecture, installation,
configuration, platform specifics, conventions, gotchas, and (for \texttt{kb})
adversarial or out-of-scope probes---topics that
stress different lanes of the hybrid retriever (documents, symbols, and facts).
Scoring has two families that both enter the harvest grade $S$
(Eq.~\ref{eq:success}):

\begin{center}\small
\begin{tabular}{@{}lp{4.0cm}@{}}
\toprule
\textbf{Axis} & \textbf{Criterion / measurement} \\
\midrule
\multicolumn{2}{@{}l@{}}{\textit{LLM-judged quality (ordinal labels $0$--$4$)}} \\
Correctness       & Factually grounded in the repo/KB \\
Usefulness        & Helps a developer act or understand \\
Relevance         & Stays on the question; free of unrelated facts \\
Specificity       & Uses concrete repo-specific details \\
Evidence Handling & Constrained to evidence; acknowledges uncertainty \\
\addlinespace
\multicolumn{2}{@{}l@{}}{\textit{Measured efficiency (numeric telemetry)}} \\
Token usage       & Weighted $T$ (in$+$out; N adds $0.1\times$cache\_read) \\
Latency           & Wall-clock duration $\tau_w$ \\
\bottomrule
\end{tabular}
\end{center}

\medskip
\noindent\textbf{How axes feed $S$.}
Correctness, usefulness, and relevance enter the adequacy term
$Q_{\text{adeq}}$ via $\varphi_\tau$ (Eq.~\ref{eq:adequacy}).
Token usage and latency become the efficiency terms $E_{\text{tok}}$ and
$E_{\text{speed}}$ (Eq.~\ref{eq:success-components}).
Specificity and evidence handling are scored and reported as diagnostics but
do not enter $Q_{\text{adeq}}$ or $S$.
The secondary pass rate counts questions where correctness, usefulness,
\emph{and} relevance are all $\geq 3$.

\medskip
\noindent\textbf{Ordinal labels, not bare numbers.}  Rather than ask the LLM
judge for ``an integer 0--4''---which invites guessing a point on an unanchored
scale---each quality axis is scored by selecting one of five \emph{named ordinal labels}.
Correctness, for example, ranges over
\textit{correct}~(4), \textit{mostly\_correct}~(3), \textit{mixed}~(2),
\textit{mostly\_wrong}~(1), and \textit{no\_answer}~(0); the other quality axes use
analogous per-axis vocabularies (e.g.\ relevance:
\textit{focused}/\textit{on\_topic}/\textit{padded}/\textit{off\_topic}/\textit{unrelated}).
This reframes scoring as classification---``which description fits this answer?''---rather
than magnitude estimation, which is markedly more reliable for LLM judges.  Each
label maps deterministically to its ordinal level $s \in \{0,1,2,3,4\}$, so the
adequacy utility (Eq.~\ref{eq:adequacy}) and every downstream metric operate on the
same $0$--$4$ scale as before and historical runs remain comparable.
Token usage and latency are measured from run telemetry and are never labeled.

\subsection{Success Score and Headline Verdict ($\Delta S$)}
\label{subsec:success}

The paired harvest evaluation's single scalar per side is $S \in [0,1]$ (higher is better).
It trades \emph{adequate} answer quality against operational cost: we care that
responses are correct and meaningful, but rubric scores above an acceptability
threshold $\tau$ yield diminishing marginal value---polishing a 3.5 into a 4.0
should not dominate token or latency savings.

\medskip
\noindent\textbf{Adequacy utility.}  Each quality axis $s \in [0,4]$ (correctness,
usefulness, relevance) maps to a normalized utility with threshold $\tau = 3$ and excellence
discount $\beta = 0.2$:

\begin{equation}
\varphi_\tau(s) = \frac{1}{1+\beta}\left(
  \min\!\left(1,\;\frac{s}{\tau}\right)
  + \beta \cdot \frac{\max(0,\; s - \tau)}{4 - \tau}
\right)
\label{eq:adequacy}
\end{equation}

\noindent Below $\tau$, quality rises linearly (inadequate answers are heavily
penalized).  At $s = \tau$, $\varphi_\tau = 1/(1+\beta) \approx 0.83$; at $s = 4$,
$\varphi_\tau = 1$.  The gap from ``acceptable'' to ``perfect'' is therefore
$\approx 17\%$ of the quality scale---not the $33\%$ implied by linear
$(c+u)/8$ scoring.

\medskip
\noindent\textbf{Composite score.}  The harvest success score blends adequacy
quality with token economy and speed:

\begin{equation}
S = w_Q \cdot Q_{\text{adeq}} + w_T \cdot E_{\text{tok}} + w_V \cdot E_{\text{speed}}
\label{eq:success}
\end{equation}

\noindent with default weights $w_Q = 0.60$, $w_T = 0.30$, $w_V = 0.10$:

\begin{align}
Q_{\text{adeq}} &= \tfrac{1}{3}\bigl(\varphi_\tau(\bar{c}) + \varphi_\tau(\bar{u}) + \varphi_\tau(\bar{r})\bigr), \notag \\
E_{\text{tok}} &= 1 - \min\!\Bigl(\tfrac{T}{B_T},\,1\Bigr), \notag \\
E_{\text{speed}} &= 1 - \min\!\Bigl(\tfrac{\tau_w}{B_\tau},\,1\Bigr)
\label{eq:success-components}
\end{align}

\noindent where $\bar{c}, \bar{u}, \bar{r}$ are mean correctness, usefulness, and relevance ($0$--$4$),
so an answer that drags in unrelated facts is penalized even when correct and useful,
$T$ is the weighted token total for the question side
($\text{input} + \text{output} + 0.1 \times \text{cache\_read}$ for control agents;
kb query uses undifferentiated input$+$output), and $\tau_w$ is
wall-clock latency.  Budgets $B_T = 10^6$ tokens and $B_\tau = 6\times 10^5$\,ms
are fixed (budget-absolute).  KB (K) and control (N) use the identical formula.

\medskip
\noindent\textbf{Headline project grade.}  The single number that answers
\emph{does KB beat a real coding agent?} is the success-score \emph{difference}
in the same evaluation run:

\begin{equation}
\Delta S = S_K - S_N
\label{eq:delta-s}
\end{equation}

\noindent $\Delta S \geq +0.02$ $\Rightarrow$ KB \textbf{ahead of control};
$\Delta S \leq -0.02$ $\Rightarrow$ \textbf{behind}; otherwise \textbf{on par}.
Per-side scores $S_K$ and $S_N$ come from Eq.~\ref{eq:success}; their component
parts ($Q_{\text{adeq}}$, $E_{\text{tok}}$, $E_{\text{speed}}$) show \emph{where} KB wins or
loses (e.g.\ adequate quality at lower exploration cost).

\medskip
\noindent\textbf{Secondary diagnostics.}  Pass rate and per-axis rubric means
(correctness, usefulness, relevance, etc.) help explain a $\Delta S$ outcome but are
not the headline grade.  We also report the fraction of questions where
correctness, usefulness, \emph{and} relevance all score $\geq 3$ on the 0--4 scale.

\medskip
\noindent\textbf{Retrieval-side relevance.}  For condition~K, we log how many
retrieved units the curator kept, dropped, and re-queried (\S\ref{subsec:curation}),
and compute retrieval precision as $\text{kept}/(\text{kept}+\text{dropped})$.
This complements answer-level relevance in the rubric: low precision with high
answer relevance indicates heavy pre-synthesis filtering; low answer relevance
despite curation signals synthesis or gap-fill gaps.

\medskip
\noindent\textbf{Scoring stability.}  LLM-as-judge scoring is
non-deterministic even at temperature~0; we average three scorer calls per question.

\noindent\textbf{Portfolio suites.}
The remaining eight repositories report paired $\Delta S$ values of
\texttt{fzf}~\FzfDeltaS, \texttt{kestra}~\KestraDeltaS,
\texttt{shellcheck}~\ShellcheckDeltaS, \texttt{lazygit}~\LazygitDeltaS,
\texttt{datasette}~\DatasetteDeltaS, \texttt{mitmproxy}~\MitmproxyDeltaS,
\texttt{fish-shell}~\FishShellDeltaS, and \texttt{brew}~\BrewDeltaS{}
($S_K$ and pass rates in Table~\ref{tab:harvest-results}).
They span Rust CLI tooling, Java/UI orchestration, Haskell AST analysis,
Go and Python TUIs, Python data products, proxy/networking code, and Ruby DSL
packaging---exercising parsers, hybrid retrieval, and UI/product inference beyond
monolithic C libraries.
Control agents vary by suite: \texttt{kb}, \texttt{raylib}, \texttt{fzf},
\texttt{shellcheck}, \texttt{lazygit}, and \texttt{fish-shell} use Cursor Agent
(\texttt{composer-2.5}); \texttt{kestra}, \texttt{datasette}, \texttt{mitmproxy},
and \texttt{brew} use Claude Code (\texttt{claude-sonnet-5}).
Each $\Delta S$ is a within-suite paired comparison; cross-suite N-side
comparisons should treat the agent backend as a confound.

\medskip
\noindent\textbf{Quality vs.\ efficiency trade-off.}  Across the portfolio the
control agent typically leads on adequacy ($Q_{\text{adeq}}$) and mean rubric
scores, while K trails on answer quality (e.g.\ kb self-check correctness
\KbSelfCheckKCorrectness{}, raylib \RaylibKCorrectness{}).
K nonetheless wins $\Delta S$ on every suite because the success score weights
token economy and latency ($w_T{=}0.30$, $w_V{=}0.10$): K's weighted token totals
are an order of magnitude smaller than N's, and K completes the query phase
faster.  The adequacy gap remains the main headroom for future retrieval and
curation work; under the fixed $S$ weights it does not overturn the efficiency
margin.

\medskip
\noindent\textbf{Retrieval cost profile.}  The hybrid retriever is a
\emph{single bounded pass}: the six lexical/neural lanes and the depth-1
document$\leftrightarrow$symbol hop are deterministic SQLite work with no LLM in
the loop, so---unlike the iterative graph-walk it replaced---retrieval no longer
consumes model tokens by exploring until an in-loop judge declares the pool
sufficient.  On the K side the only LLM calls are the curator's structured
relevance verdict (plus any bounded gap re-queries) and the one-shot synthesis
call; per-question telemetry records the thinking-vs-synthesis token split and
the curator's kept/dropped/re-queried counts (retrieval precision,
Table~\ref{tab:harvest-results}).  Removing the unbounded loop is what keeps
K-side weighted token totals an order of magnitude below the control agent's
while retrieval cost stays bounded by the candidate pool rather than by index
connectivity.
